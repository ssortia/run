# RunTimer

Обзор, структура и установка описаны в `README.md`, сценарии в `USER_STORIES.md`. Дизайн-макет экранов: https://claude.ai/artifact/WKnsAn8dCvkNbCqtUVcdik, прототипы иконки приложения: https://claude.ai/artifact/PBGGxgEGYZKHq1BBvPQRpx (читаются инструментом Artifact, `action: "read"`).

## Команды

```bash
./gradlew test assembleDebug   # тесты обоих вариантов и APK
./gradlew lintDebug            # lint
./gradlew testDebugUnitTest --tests 'com.ssortia.runtimer.WorkoutTest'   # один класс тестов
```

JDK 17 не прописан в профиле оболочки, и `java` нет в `PATH`. На этой машине JDK лежит в `~/.local/jdk-17`, на других путь свой: `JAVA_HOME=~/.local/jdk-17 ./gradlew test`.

Эмулятора и устройства в окружении нет. Звук, работу при выключенном экране и уведомления можно проверить только вручную на телефоне, не считайте их подтверждёнными по сборке и тестам.

## Соглашения

- Комментарии, строки интерфейса и документация на русском.
- Логика живёт в чистых функциях и классах без Android API и покрывается unit-тестами. Подписи и строки передаются в них параметрами. Код с Android API (сервис, Compose, Room, `AudioTrack`, `Vibrator`) держим тонким, он тестами не покрыт.
- KDoc только там, где поведение неочевидно.
- Настройки приложения (громкость сигналов, вибрация, приглушение музыки, задержка старта, тема) хранятся отдельными ключами в `SettingsStore`, а не в `WorkoutSettings` и не в интенте: сервис читает их в `startWorkout` и при выключенной вибрации не создаёт `Buzzer`, а при громкости 0 (`isSoundOn`) не создаёт `Beeper`: иначе он брал бы аудиофокус ради неслышного сигнала. Без `Beeper` из-за нулевой громкости предупреждения о звуке не показываются (`soundFailedWarning`, `soundMutedWarning`), пробного сигнала на 0 тоже нет. Громкость `snapVolume` приводит к шагу 10 с округлением половины вверх, в том числе старые значения с шагом 5. Числовые значения прижимаются к диапазону и при чтении, и при записи. Задержка старта выбирается из списка `START_DELAY_OPTIONS_SEC` с неравномерным шагом: ползунок ходит по индексам, а `snapStartDelay` приводит любое значение, в том числе старое 7 или 25, к ближайшему из списка.
- Планы лежат в `docs/plans/`, после ревью переносятся в `docs/plans/completed/`. Задачи лежат в `docs/tasks/`, выполненные переносятся в `docs/tasks/completed/`: выполненной считается задача, где осталась только ручная проверка на телефоне.
- При составлении плана через скил `planning:make` не спрашивайте, писать ли код по TDD или сначала код: по умолчанию сначала пишется код, затем тесты к нему. После создания плана не спрашивайте, что делать дальше (интерактивное ревью, авто ревью, implement, done): всегда сразу запускайте авто ревью. После авто ревью не предлагайте интерактивное ревью, оставьте на выбор только implement и done. При старте реализации не спрашивайте, работать интерактивно или автономно: план всегда реализуется автономно.
- При старте `planning:exec` не спрашивайте, останавливаться ли после каждого коммита для проверки кода: всегда выбирайте вариант «auto-commit» и выполняйте план полностью автоматически.

## Архитектура

Три слоя с однонаправленным потоком данных: UI (`MainActivity`, Compose-экраны), сервис (`WorkoutService`), логика, звук, вибрация и история (`Workout`, `WorkoutClock`, `tickAt`, `Beeper`, `Buzzer`, `runRecordOrNull`, `RunHistory`). `WorkoutClock` считает время тренировки за вычетом пауз, `Buzzer` дублирует сигналы вибрацией. Состояние лежит в `WorkoutService.state` в `companion object`, привязка к сервису не нужна. ViewModel и DI не используются намеренно: сервис один, а экран тренировки выбирается по состоянию. `WorkoutScreen` — общая оболочка навигации на Navigation Compose, она составляется во всех состояниях (`Idle`, `Countdown`, `Active`), поэтому стек и сохранённые состояния вкладок переживают старт и финал тренировки. `rememberNavController()` и маршрут (`currentBackStackEntryAsState()`) живут в оболочке: системные панели выбираются по слою тренировки (см. ниже), маршрут на них не влияет. В оболочке `NavHost` с четырьмя строковыми маршрутами `settings` (стартовый), `app_settings`, `history` и `progress`, их константы и вкладки (`BottomTab`, `bottomTabOf`) лежат в `ui/BottomTab.kt`. Под `NavHost` стоит `NavigationBar` с вкладками «Таймер» (`settings`), «История», «Прогресс» и «Настройки» и центральным слотом между «Историей» и «Прогрессом», где лежит доступный заместитель центральной кнопки («Старт» или пауза, см. «Неочевидное»); выбранная вкладка берётся из этого маршрута (`BottomBar` получает её параметром). Центральная кнопка не вкладка: в `BottomTab` и `NavHost` её нет, видимая кнопка `CenterFab` лежит поверх панели. Вкладки переключаются по схеме `navigate(route) { popUpTo(ROUTE_SETTINGS) { saveState = true }; launchSingleTop = true; restoreState = true }`: в стеке не больше двух записей, «Назад» с любой вкладки ведёт на «Таймер» (форму), с него закрывает приложение (развёрнутый экран тренировки «Назад» сначала сворачивает, см. ниже), а запись `settings` остаётся в стеке. Переход на вкладку — `navigateToTab` в `WorkoutScreen.kt`, на текущую вкладку он ничего не делает, и это единственная такая проверка для панели. Состояние вкладки (`rememberSaveable`, прокрутка) при переходе на другую вкладку сохраняется и возвращается через `restoreState`, а системная «Назад» снимает запись без сохранения, и следующее открытие вкладки начинается заново. Каждому маршруту `NavHost` соответствует вкладка `BottomTab`, `BottomTabTest` сверяет их набор. Иконка и подпись выбранной вкладки берут `primary`: индикатор M3 по умолчанию (`secondaryContainer` на `surfaceContainer`) в светлой теме почти не виден. Внешний `Box` оболочки отступов не применяет, его высоту `onSizeChanged` отдаёт в `sheet.heightPx`, путь слоя тренировки (`onSizeChanged`, а не `BoxWithConstraints`: лишняя субкомпозиция над `NavHost` не нужна). Отступы `safeDrawing` сверху и по бокам поглощает внутренний `Box` (в нём `Column` с `NavHost`, полоской тренировки и панелью и поверх них `CenterFab`) через `windowInsetsPadding(...only(Top + Horizontal))`, именно `windowInsetsPadding`, чтобы `NavigationBar` не добавил боковые второй раз, и именно `Box`, а не `Column`, чтобы при боковой системной панели центральная кнопка стояла по центру панели, а не экрана; снизу системную панель учитывает сам `NavigationBar` своими `windowInsets` по умолчанию. Слой тренировки — второй ребёнок внешнего `Box`, вне этих отступов: их поглощает `TimerLayout`, и фон отрезка уходит под системные панели. Клавиатуры в приложении нет (повторы меняются только кнопками), отдельный учёт `ime` не нужен. У экранов нет стрелки «Назад», у `AppTopBar` нет `onBack`, у формы в слоте `actions` плашка недели (`WeekChip`), открывающая шторку программы. Экраны отсчёта и тренировки маршрутами не становятся: маршрут `settings` («Таймер») всегда показывает форму, а `CountdownContent` и `ActiveContent` лежат в слое оболочки `WorkoutLayer` поверх внутреннего `Box`. Отдельный маршрут `workout` отвергнут: экран, идущий за пальцем, и доезд от текущего смещения делаются одним смещением, а переход `NavHost` начинает анимацию с нуля, к тому же его анимации отключены (см. «Неочевидное»). Развёрнутость и смещение слоя держит `WorkoutSheetState` (`ui/WorkoutSheetState.kt`), его создаёт `MainActivity` через `rememberWorkoutSheetState(initialExpanded = state !is Idle)` и передаёт в `WorkoutScreen` параметром `sheet`: по нему выбираются системные панели, и источник должен быть один. Сохраняется только `expanded` (`rememberSaveable` с `Saver`), поэтому восстановленная activity (поворот, гибель activity системой с сохранённым состоянием) остаётся свёрнутой или развёрнутой, как её оставили, а развёрнутой во время тренировки открывается только activity без сохранённого состояния (например, после выхода «Назад» и нажатия на уведомление). Чистые правила слоя лежат в `ui/WorkoutSheet.kt` (тесты в `WorkoutSheetTest`). Признак `isWorkoutFullscreen(state, expanded)` (`!Idle && expanded`, единственное место этой формулы) считают и `MainActivity` (панель навигации), и `WorkoutScreen` (слой); второго источника нет. По нему оболочка составляет слой (свёрнутый не составляется вовсе) и скрывает от TalkBack внутренний `Box` (`clearAndSetSemantics {}`: вкладка, полоска, панель с заместителем центральной кнопки). `expanded` становится `true` в начале разворачивания и `false` только после доезда сворачивания: снизу слой закрывает панель навигации всё это время, поэтому её стиль (`navigationBarStyle`) выбирается по `isWorkoutFullscreen(state, sheet.expanded)`. Строка состояния вверху закрыта слоем только у самого верха, поэтому значки строки состояния берут `darkStatusIcons(state, darkTheme, isWorkoutFullscreen(state, layerUnderStatusBar))`, где `layerUnderStatusBar` — `sheetCoversStatusBar(expanded, offsetPx, statusBarPx)` в `derivedStateOf` (смещение меньше высоты строки состояния `WindowInsets.statusBars`, не меньше 1 px): пока слой выезжает, сворачивается или его держит палец, сверху видна вкладка, и значки следуют за ней; `derivedStateOf`, потому что смещение меняется каждый кадр. Вне полноэкранного режима и в `Idle` значки как на форме, `!darkTheme`. TalkBack-скрытие вкладок включается в начале разворачивания, пока слой ещё внизу, это принято. Смещение — `mutableFloatStateOf` в пикселях (0 развёрнут, `heightPx` свёрнут), не сохраняется: после поворота развёрнутый слой стоит на месте, а сворачивавшийся в момент поворота снова развёрнут целиком (`expanded` ещё `true`), это принято. Анимация одна на слой (`Job` в `animation`, новая отменяет прежнюю), это `animate(...)` с `tween(SHEET_ANIMATION_MS = 280, FastOutSlowInEasing)` в `rememberCoroutineScope`; кадр уже отменённой анимации отбрасывается проверкой `isActive`, иначе он перебил бы палец. `expand()` при `!expanded` ставит слой под нижний край (`offsetPx = heightPx`) и выставляет `true`, затем едет к 0; из сворачивания (`expanded` ещё `true`) он разворачивается от текущего смещения без скачка вниз. `collapse()` едет к `heightPx` и затем выставляет `false`; прерванное новым `expand()` или пальцем оно бросает `CancellationException`, и `false` не выставится, повтор идемпотентен. Сворачивают кнопка «Свернуть» (`TextButton` слева сверху цветом `colors.content`, `onCollapse` у `TimerLayout`), системная «Назад» и свайп вниз, разворачивают полоска и старт. Сворачивание не трогает стек: под слоем остаётся та вкладка, где нажали «Старт» или куда перешли позже. При старте слой разворачивается только на переходе из `Idle` (`shouldExpandWorkout(wasIdle, idle)` в `LaunchedEffect(idle)`): прошлое значение `wasIdle` лежит в `rememberSaveable`, иначе поворот во время тренировки разворачивал бы свёрнутый экран. Переход идёт по смене состояния, а не в колбэке «Старта»: старт может прийти после запроса разрешения в новый экземпляр activity. После финала или «Стоп» (`idle`) слой убирается без анимации: `reset()` отменяет анимацию и выставляет `false`, вкладка не меняется (смещение не сбрасывается: следующий `expand()` всё равно ставит слой под нижний край). Нажатие на уведомление открывает activity как есть (`singleTop`, `onNewIntent` не обрабатывается): живая activity остаётся как её оставили, свёрнутой или развёрнутой, а экземпляр без сохранённого состояния получает развёрнутый слой. Свайп: палец меняет смещение синхронно в `dragBy` (`sheetDragTo` прижимает его к `0..heightPx`, поглощённая часть — разница нового и прежнего смещения), а первое движение пальца останавливает идущую анимацию, поэтому захват слоя на ходу не теряет первые пиксели и следующее событие того же кадра считается от нового смещения. `Modifier.draggable(Orientation.Vertical)` слоя через `rememberDraggableState { sheet.dragBy(it) }`, при отпускании `settle(velocity)`: `shouldCollapseSheet(offsetPx, heightPx, velocityPx, flingVelocityPx)` решает, сворачивать или вернуть наверх: флинг важнее смещения (порог `SheetFlingVelocity` 125 dp/с, как у шторок M3, в пиксели через `LocalDensity` в `rememberWorkoutSheetState`, передаётся в состояние в `SideEffect`), без флинга порог `SHEET_COLLAPSE_FRACTION` (четверть высоты), при `heightPx <= 0` не сворачивать. Одного `draggable` мало: в foundation 1.7 `verticalScroll` колонки `TimerLayout` начинает перетаскивание и тогда, когда прокручивать некуда, и непрокрученный остаток уходит только по nested scroll, мимо `draggable`, поэтому свайп по цифрам времени не сворачивал бы экран и в портретной ориентации. Его ловит `nestedScrollConnection` состояния по образцу шторок M3: `onPreScroll` вверх сначала поднимает опущенный слой (`sheetTakesPreScroll`), `onPostScroll` вниз только от пальца (`NestedScrollSource.UserInput`, `sheetTakesPostScroll`) опускает его остатком, `onPreFling` при опущенном слое (`sheetTakesFling`) решает жест сам и поглощает скорость. `onPostFling` намеренно не переопределён: foundation вызывает его после `onPreFling` в том же жесте, слой ещё опущен (анимация только запущена), и второе решение по нулевой скорости отменило бы первое, флинг вниз с малым смещением вернул бы слой наверх. `AnchoredDraggableState` не используется: в foundation 1.7 он `@ExperimentalFoundationApi`, а в 1.8 его API поменялся, и обновление BOM сломало бы свайп. Порядок модификаторов слоя важен: `offset { IntOffset(...) }` первым (область касаний едет со слоем, смещение читается при размещении, поэтому анимация не перекомпоновывает слой), затем `nestedScroll`, `draggable`, а в `WorkoutLayer` пустой `pointerInput(Unit) {}`: у `TimerLayout` только фон, и без обработчика указателя касание пустого места слоя дошло бы до вкладки под ним, это не лишний модификатор. У слоя `semantics { paneTitle }` (`pane_workout` «Тренировка»): TalkBack объявляет панель и переводит в неё фокус, иначе он остался бы на скрытой полоске. `BackHandler` сворачивания стоит внутри `WorkoutLayer`, то есть в композиции после `NavHost`: Navigation Compose регистрирует свой обработчик «Назад» при стеке больше одной записи, а диспетчер вызывает последний добавленный включённый, и обработчик, составленный раньше `NavHost`, на «Истории» проиграл бы ему, «Назад» сняла бы запись стека вместо сворачивания. Включать его отдельно не нужно: слой составлен только во весь экран. Построитель `NavHost` не захватывает `state`: граф пересобирается при каждой смене лямбды-построителя, а состояние сервиса меняется каждую секунду, поэтому маршруты читают его через `rememberUpdatedState` (`currentState`), а проверку формы через `derivedStateOf` (`settingsError`). Переходы между вкладками и возврат по стеку идут только через `NavController`, слой тренировки стек не трогает. Колбэки внутри экранов `NavHost` обёрнуты в `dropUnlessResumed`, иначе двойное нажатие положит два экрана в стек или оставит пустой `NavHost`. У вкладок нижней панели, полоски тренировки и центральной кнопки обёртки нет намеренно: панель стоит вне `NavHost`, её `LocalLifecycleOwner` — activity, а не запись стека, и обёртка не следила бы за переходом между экранами. Двойное нажатие безопасно и так: переход идемпотентен благодаря `popUpTo` и `launchSingleTop`, нажатие на текущую вкладку ничего не делает, а `popBackStack` вкладки не вызывают; повторный «Старт» отсекают `permissionPending` и сервис, отклоняющий второй запрос на старт, а команды паузы явные и безопасны при повторе. Колбэки слоя тренировки («Свернуть», «Стоп», «Пауза») тоже без `dropUnlessResumed`: слой вне `NavHost`, а повтор безопасен (сворачивание идемпотентно, команды сервиса явные). Единственный свой `BackHandler` — у слоя тренировки, на свёрнутом экране системную «Назад» обрабатывает стек. Настройки формы (`WorkoutSettings`) хранит не запись стека, а оболочка: `rememberSaveable(stateSaver = WorkoutSettingsSaver) { mutableStateOf(loadSettings()) }` над `NavHost`, потому что «Старт» в панели виден на всех вкладках и запускает текущие, в том числе несохранённые, настройки (`onStart(settings)`), а его доступность `centerButtonEnabled(mode, settingsValid)` в `ui/BottomTab.kt`. `SettingsContent` получает `settings` и `onSettingsChange`, раскрытая карточка и шторка программы остаются в `rememberSaveable` записи стека. Оболочка при старте не покидает композицию, поэтому после тренировки настройки не перечитываются из `SettingsStore`: `onStart` сохранил их до старта, а во время тренировки правки формы остаются в оболочке до следующего «Старта». Параметры на отсчёте полоска берёт не из формы, а из `SettingsStore`, откуда их взял сервис: `remember(idle) { loadSettings().toWorkout() }` читает их один раз на уходе из `Idle`, потому что форму можно успеть поправить до публикации отсчёта (например, за диалогом разрешения), а во время тренировки форма доступна, и полоска не должна за ней следовать. Экран тренировки лежит слоем вне `NavHost`, поэтому старт и финал не выводят `SettingsContent` из композиции, и его `rememberSaveable` (раскрытая карточка, шторка, прокрутка) переживает тренировку. Текст ошибки показывается только на форме.

История пробежек: `RunRecord` одновременно чистая модель и `@Entity` Room, `RunDatabase.kt` содержит DAO, базу и `object RunHistory` (`runs`, `save`, `delete`). Экземпляр базы один на процесс и строится в `@Synchronized` функции `RunHistory`, а не в `by lazy`: для `Room.databaseBuilder` нужен контекст. Экземпляр берётся в вызывающем потоке до `launch`. Поля карточки собирает `runRowText` в `RunRowText.kt`, там же `groupRunsByMonth` группирует уже отсортированный список по месяцу старта в переданной зоне. Поток записей объявлен в `MainActivity` как `runs by lazy`, `HistoryContent` получает готовый список и про Room не знает. Схема экспортируется в `app/schemas/` через аргумент KSP и лежит в git, `fallbackToDestructiveMigration` не включён: смена `RunRecord` требует новой версии базы и миграции.

Прогресс по программе не хранится: маршрут `progress` собирает тот же поток `runs`, что и `history`, и считает `programProgress(records)` в `remember(records)`, поэтому удаление записи в истории сразу меняет прогресс, а схема базы для него не нужна. `programProgress` в `ProgramProgress.kt` отдаёт все 10 недель по порядку, считает только завершённые пробежки и не зависит от порядка списка (дата последней — максимум `startedAtMs`). Неделя пройдена при `RUNS_TO_PASS_WEEK` (4) пробежках, до этого у текущей недели кольцо узла и деления карточки закрашивают по части на пробежку, дальше четырёх не растут. Текущую неделю считает `currentProgramWeek(runs)`: неделя завершённой пробежки по программе (`presetWeekOf` не `null`) с наибольшим `startedAtMs`, при равенстве большая неделя, без таких пробежек неделя 1, поэтому «Сейчас» есть всегда и удаление записи может её сменить. `WeekProgress` несёт обязательные `current` и `beforeCurrent` (неделя выше текущей), из них и `passed` выводятся вид узла `mark` (`WeekMark`: `CURRENT` важнее `PASSED`, затем `SKIPPED` выше текущей и `AHEAD` ниже) и `lineToNextFilled`: отрезок линии к следующей неделе закрашен выше текущей или под пройденной, у последней недели его нет. Отрезки выше и ниже узла каждой строки раздаёт `lineSegments(progress)` (`LineSegments`, `null` у первой недели сверху и у последней снизу). Экран эти правила не повторяет, только рисует. `WeekProgress` несёт свой `WorkoutPreset`, поэтому экран строит строки по `progress`, не сопоставляя его с `WORKOUT_PRESETS` по позиции. `ProgressContent` получает готовый `List<WeekProgress>?` и про Room не знает, при `null` показывает только `AppTopBar`. Текст карточки недели (заголовок, параметры, число пробежек или «—» (`ProgressLabels.none`) без пробежек, дата или `null`, строка состояния `status` только у текущей: «Пробежек N из 4» до порога и «Неделя пройдена · N раз» с настоящим числом с порога, и `description` всей строки одной фразой для TalkBack, с параметрами недели после заголовка, например «Неделя 3, Бег 3:00 · Шаг 2:00 · ×5, сейчас, пробежек 3 из 4, последняя 3 ноября»; строка ленты ставит его через `clearAndSetSemantics`, поэтому видимые число, дата, узел, линия и деления не читаются) собирает `progressRowText` в `ProgressRowText.kt`, дата последней пробежки форматируется там же явным шаблоном `d MMMM`, склонение «раз» идёт ресурсом `<plurals>` и передаётся готовой строкой, подписи описания со строчной буквы приходят через `ProgressLabels`.

## Контракт сервиса

Нарушение этих правил даёт крэш или зависшую тренировку, а тесты его не поймают.

- `startForeground` идёт первым в `onStartCommand`, до всех проверок, даже если запрос будет отклонён. Заголовок берётся из последнего показанного текста `shownText`, а `app_name` только у нового экземпляра: на паузе текст не меняется, и цикл не вернул бы уведомление после команды.
- Команды паузы (`pauseIntent`, `resumeIntent`) идут через `startService()`: сервис уже на переднем плане. Они явные, а не переключатель, и безопасны при повторе. Без активной тренировки команда не содержит параметров и отклоняется существующим `stopSelf(startId)`, до создания `WorkoutClock` (отсчёт) и в финальном хвосте она ничего не меняет. Если команда пришла в уже уничтоженный экземпляр (например, «Стоп» и «Пауза» в одном кадре), система создаёт новый, и тот до `stopSelf(startId)` успевает показать уведомление с названием приложения (`app_name`). Поэтому кнопка паузы недоступна после финального сигнала (`pauseEnabled`).
- UI останавливает сервис только через `stopService()`, сам сервис завершается через `stopSelf()`. Вызов `startForegroundService()` ради остановки приведёт к крэшу.
- `onStartCommand` всегда возвращает `START_NOT_STICKY`. Потеря тренировки при гибели процесса принята для первой версии.
- `Countdown` и `Active` публикуются только после `startForeground`, иначе «Стоп» появится раньше времени.
- Окончательно ресурсы освобождает только `onDestroy`: отменяет цикл, отпускает `Beeper`, `Buzzer` и wake lock, снимает уведомление и последним ставит `Idle`. Финал лишь вызывает `stopSelf()`, поэтому форма появляется уже после освобождения ресурсов. Единственное исключение: на паузе wake lock снимается временно и при продолжении берётся заново на остаток тренировки плюс запас, поэтому `onDestroy` проверяет `isHeld`.
- `job` не обнуляется после финала: до `onDestroy` новый запрос на старт отклоняется.
- Запись истории собирается в `onDestroy` сразу после `scope.cancel()`, до остальных шагов: `saveRun()` берёт длительность из `clock.elapsedAt(...)`, а `workout` и `runStartedAtMs` из полей: оба заполнены раньше `clock`, поэтому проверяется только он. Сбой `RunHistory.save` ловится в `saveRun()` и пишется в лог, иначе `onDestroy` оборвался бы до освобождения ресурсов и `Idle`. Без `clock` (отклонённый запрос, команда паузы без тренировки, «Стоп» во время отсчёта) запись не собирается. Сохраняет её `RunHistory.save` в собственной области корутин на `Dispatchers.IO`, потому что `scope` сервиса уже отменён, без отдельного wake lock: после `onDestroy` процесс без сервиса может быть завершён, и wake lock от этого не спасает, а сон процессора только приостановит короткую вставку. `runStartedAtMs` заполняется перед созданием `WorkoutClock` и пересчитывается к моменту `startedAt` через `wallTimeAt`.

## Неочевидное

- `Beeper`: перед каждым проигрыванием нужны `stop()` и `reloadStaticData()`, иначе повторный сигнал будет беззвучным.
- `Beeper` берёт аудиофокус заранее через `duck()`: сервис вызывает его на каждом шаге цикла, когда до сигнала осталось не больше `DUCK_AHEAD_MS` (`shouldDuck`), и в конце отсчёта, иначе `stopDucking()`. `play()` переводит фокус на таймер возврата `soundWithTailMs`, а `duck()` этот таймер снимает, поэтому на коротких отрезках музыка остаётся приглушённой. `duck()` ничего не делает, если сигналы не готовы (`isReady`), и считает фокус взятым (`holding`) только при `AUDIOFOCUS_REQUEST_GRANTED`, поэтому после отказа следующий шаг цикла запросит его снова. Если `play()` не смог проиграть сигнал, он сразу возвращает фокус, взятый через `duck()`: таймера возврата в этом случае нет. Пауза возвращает фокус сразу в `handlePauseAction`, до снятия wake lock, а продолжение сразу приглушает музыку, если до сигнала не больше `DUCK_AHEAD_MS` (`shouldDuckAfterResume`): цикл без wake lock может не проснуться, а на следующем шаге приглушать уже поздно. Окончательно фокус отпускает `release()`, у `Beeper` сервиса это `onDestroy`. Каждый отрезок кончается сигналом, поэтому сервис считает время до сигнала по `position.remainingMs`; если это изменится, `shouldDuck` надо кормить другим временем. Настройка «Приглушать музыку» передаётся обеим функциям обязательным `duckMusic` и в конструктор `Beeper`: при `false` фокус не берут ни `duck()`, ни `play()`, и сигнал звучит поверх музыки в полную громкость. Её хранит прежний ключ `duck_ahead`, чтобы сохранённое значение не сбросилось.
- Пробный сигнал ползунка играет собственный `Beeper` в `MainActivity`, он готовит только `INTERVAL`. Его отпускают перед новым пробным сигналом, при уходе состояния из `Idle` и в `onStop`, иначе дорожка и аудиофокус переживут экран или будут жить всю тренировку рядом с `Beeper` сервиса. Во время тренировки ползунок громкости доступен, но `saveVolumeAndPreview` при `WorkoutService.state.value !is Idle` только сохраняет громкость: ни пробного сигнала, ни `Toast` о нулевой громкости медиа, иначе два `Beeper` спорили бы за аудиофокус. Сервис читает сигналы и задержку старта в `startWorkout`, поэтому `AppSettingsContent` получает `workoutRunning` и под группами «Сигналы» и «Тренировка» показывает `hint_next_workout` «Применится к следующей тренировке»; тема применяется сразу, подписи под ней нет. Все методы `Beeper` вызываются только из главного потока: таймер возврата фокуса работает на `Handler(Looper.getMainLooper())`.
- Канал `Beeper` (`USAGE_ASSISTANCE_NAVIGATION_GUIDANCE`) считается следующим громкости медиа, поэтому `isMediaMuted()` и `volumeControlStream` в `MainActivity` смотрят на `STREAM_MUSIC`. При смене атрибутов `Beeper` обе строки надо пересмотреть, тесты это не поймают.
- Атрибуты `Beeper` объявлены в `companion object`, до `tracks`: поле экземпляра ниже `tracks` было бы ещё `null`, `AudioTrack.Builder` бросил бы исключение, и `catch` молча оставил бы тренировку без сигналов при зелёных тестах.
- Итоговая громкость сигнала равна настройке приложения, умноженной на системную громкость канала: `setVolume()` только ослабляет звук.
- Звуки отсчёта, старта, смены отрезка и финала (`signal_countdown`, `signal_start`, `signal_interval`, `signal_finish`) лежат в `res/raw` и должны быть WAV PCM 16 бит моно 44,1 кГц, иначе `decodeWav` их отклонит и сигнала не будет. Звук отсчёта должен быть короче 1 с: «2» и «1» идут с интервалом в секунду, `SignalFilesTest` это проверяет. Их длительности продублированы константами `COUNTDOWN_SOUND_MS`, `START_SOUND_MS`, `INTERVAL_SOUND_MS` и `FINISH_SOUND_MS`, потому что по ним держится фокус и ждёт финал, а файлы читаются только с Android API. `SignalFilesTest` сверяет константы с файлами, при замене звука обновите обе. Файлы готовились так: `ffmpeg -i in.mp3 -af "atrim=start=0.06:end=…,asetpts=N/SR/TB,pan=mono|c0=0.5*c0+0.5*c1,aresample=44100,afade=t=in:d=0.005,afade=t=out:st=…:d=0.03" -c:a pcm_s16le -map_metadata -1 tmp.wav && sox tmp.wav out.wav gain -n -2`.
- `FINISH_TAIL_MS` нельзя убирать: `release()` сразу после конца буфера обрезает финальный сигнал.
- `START` подаётся отдельным вызовом в `runLoop`, мимо `tick.signal`, и правило «только при задержке > 0» тестами не покрыто. `COUNTDOWN` («2» и «1») выдаёт `countdownTickAt` при пересечении границ `COUNTDOWN_SIGNALS_AT_MS` с прошлого шага (`previousRemainingMs`), и `runCountdown` проигрывает его отдельно от цикла тренировки. Всё новое, что реагирует на сигналы, надо добавлять во все три места (`runCountdown`, `START` в `runLoop`, `tick.signal`), как сделано для `Buzzer`. В отсчёте приглушение считается по `msToNextCountdownSignal`, а не по времени до старта: первый сигнал звучит за 2 с до него.
- Ожидание после финала равно большей из длительностей звука и вибрации плюс `FINISH_TAIL_MS`: что из них длиннее, зависит от звука финала и паттернов, а `onDestroy` оборвала бы более длинное.
- Во время отсчёта `startedAt` лежит в будущем, поэтому `WorkoutClock` создаётся в `runLoop` только после отсчёта: иначе прошедшее время было бы отрицательным. Команда паузы может прийти раньше, поэтому без часов `handlePauseAction` её игнорирует (`clock ?: return`).
- На паузе wake lock снимается сразу, хотя `Beeper` может ещё держать фокус до `soundWithTailMs`, а его таймер на `Handler` во сне процессора стоит. Это допустимо: пока играет музыка, её вывод сам не даёт процессору уснуть, а без музыки удержанный фокус никому не мешает.
- `Buzzer` вызывает перегрузку `vibrate(VibrationEffect, AudioAttributes)` с `@Suppress("DEPRECATION")` намеренно: замена с `VibrationAttributes` есть только с API 33, а `USAGE_ALARM` нужен, чтобы система не глушила вибрацию при выключенном экране и в беззвучном режиме. Атрибуты `Beeper` (`USAGE_ASSISTANCE_NAVIGATION_GUIDANCE`) для вибрации не подходят по той же причине.
- Правило допустимых параметров записано дважды: в `WorkoutSettings.validate()` для формы и в `workoutOrNull()` для сервиса. Меняйте их вместе, иначе форма пропустит настройки, а сервис молча отклонит запрос. Нулевой шаг допустим только при одном повторе (неделя 10 программы).
- Неделя записи истории (`presetWeekOf(record)`) определяется сравнением `Workout` записи с `preset.settings.toWorkout()`, а шаг берётся из `RunRecord.effectiveWalkSec`, который при одном повторе даёт 0: такой шаг не выполняется (по тому же правилу его не показывает `runRowText`), а форма разрешает его задать, поэтому «Бег 30:00, Шаг 2:00, ×1» засчитывается неделе 10. Сравнение через `toWorkout()` нужно, чтобы 1 мин 30 сек недель 5–6 совпадали с 90 секундами записи. Цвета экрана прогресса: закрашенные части кольца, деления, круги пройденных и пропущенных недель, обводка кольца недели впереди с пробежками и закрашенные отрезки линии берут `segmentColors(isRun = true, …).marker`, а не `primary`, незакрашенные `progressTrackColor`, галочка и прочерк пропущенной недели (`SKIPPED`) `progressCheckColor` из `ui/Theme.kt`. Прочерк нарисован `drawLine` в `Canvas`: минуса в `material-icons-core` нет. Узлы стоят поверх линии на круге цвета `background`, чтобы линия под ними не просвечивала. `ThemeTest` в обеих темах требует контраст `marker` на дорожке не меньше 3:1, дорожки на `surfaceContainer` не меньше 1,3:1 (дорожка фоновая, смысл несут закрашенные части и подпись) и галочки на `marker` не меньше 3:1. Линия и узлы недель впереди лежат на фоне окна, а не на карточке, поэтому отдельная проверка в `ThemeTest` на фоне окна (`window_background_light`/`_dark` из `colors.xml`, его читает вспомогательная функция теста) требует `marker` не меньше 3:1 (закрашенная линия несёт смысл) и дорожки не меньше 1,3:1; ради неё светлая дорожка `ProgressTrackLight` затемнена до `#D4D4D0` (прежняя `#DCDCD8` на фоне `#F5F5F3` давала около 1,26:1). При смене фона окна, дорожки или `marker` пересчитайте обе проверки.
- Линия ленты прогресса рисуется в каждой строке своя: `Row(height(IntrinsicSize.Min))` с колонкой узла (`NodeColumnWidth`) и `drawBehind` на высоту строки, верхний отрезок до центра узла по `lineToNextFilled` предыдущей недели, нижний от центра по своей, у первой недели верхнего нет, у последней нижнего. Промежуток 8 dp между карточками (`WeekGap`) задаёт `spacedBy` колонки вне строк, поэтому в нём линия прерывается намеренно, как в макете: не «чините» это сплошной линией на всю колонку. Центр узла совпадает с серединой строки заголовка: верхний отступ карточки плюс половина `lineHeight` стиля заголовка через `LocalDensity`, у карточки «Сейчас» половина большего из `lineHeight` и высоты плашки (`NowChipHeight`), поэтому узел не съезжает при крупном системном шрифте; при смене отступов или стиля заголовка карточки пересчёт идёт сам, а новая вёрстка заголовка должна сохранить это правило.
- Неделя в `RunRecord` не хранится: `presetWeekOf(record)` вычисляет её по текущему `WORKOUT_PRESETS`, поэтому смена параметров недели задним числом меняет прогресс, а старые записи с прежними параметрами перестают засчитываться. Тройки (бег, шаг с учётом `effectiveWalkSec`, повторы) у недель должны оставаться разными, иначе запись достанется первой из совпавших.
- Значения по умолчанию в `WorkoutSettings` совпадают с неделей 1 из `WORKOUT_PRESETS`, поэтому при первом запуске она отмечена в шторке программы и написана на плашке справа от заголовка формы (при несовпадении с неделями там «Своя тренировка»). При смене значений по умолчанию или программы `WorkoutPresetTest` это поймает.
- `MainActivity.startWorkout()` читает настройки из `SettingsStore`, а не из замыкания: ответ на запрос разрешения может прийти в новый экземпляр activity.
- `permissionPending` блокирует второй запрос разрешения: система отклоняет его сразу, и тренировка запустилась бы за диалогом.
- Тема (`ThemeMode`) хранится ключом `theme_mode` по имени значения, неизвестное имя читается как `SYSTEM`. Выбор держит `MainActivity` в состоянии Compose, а не экран настроек: он применяется ко всему UI сразу. Признак тёмной темы считается только там (`isDarkTheme(mode, isSystemInDarkTheme())`) и раздаётся через `LocalDarkTheme` из `RunTimerTheme`; прямой вызов `isSystemInDarkTheme()` в экране разведёт цвета отрезков с выбранной темой. Системная панель навигации (`navigationBarStyle` в `enableEdgeToEdge`) и фон окна тоже задаются по этому признаку, а не по системной теме. Стиль панели выбирается по `isWorkoutFullscreen`, а не по `Idle`: вне полноэкранного режима (форма и любые вкладки, в том числе во время тренировки) `light`/`dark` с прозрачным цветом: под ней лежит фон `NavigationBar`, а подложка кнопок, в том числе принудительный контраст API 29+ у стиля `auto`, сделала бы полосу двухцветной (значки строки состояния переключаются позже, когда слой доедет до верха, см. `sheetCoversStatusBar` в «Архитектуре»). На экране отсчёта и тренировки во весь экран остаётся `auto` с подложкой: фон цветной, а значки панели следуют за темой. На API 31+ выбор дополнительно передаётся `UiModeManager.setApplicationNightMode()` (`SYSTEM` это `MODE_NIGHT_AUTO`): система применяет его к окну и заставке до старта процесса, а пересоздания activity нет: она объявляет `configChanges="uiMode"`, иначе смена темы давала чёрный кадр. Поэтому всё, что зависит от темы, должно браться из Compose (`LocalConfiguration`, `LocalDarkTheme`) или переприменяться по признаку в `setContent`, как фон окна и системные панели: тема окна из `values-night` после запуска уже не обновится. В `onCreate` он не повторяется, поэтому после восстановления настроек из резервной копии заставка может быть в системной теме до следующей смены. Константы `MainActivity.kt` уровня файла не должны вызывать Android API (`Color.argb`): файл загружается в unit-тестах, и инициализатор уронил бы их.

Уходящий экран всё равно остаётся в композиции кадр-другой, поэтому маршруты объявляются через `screen()` с непрозрачным фоном, а не через `composable()` напрямую, иначе экраны на миг накладываются.

Правило 30 секунд (`MIN_STOPPED_RUN_MS`) считается по времени без пауз.
