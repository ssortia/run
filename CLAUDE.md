# RunTimer

Обзор, структура и установка описаны в `README.md`, сценарии в `USER_STORIES.md`. Дизайн-макет экранов: https://claude.ai/artifact/WKnsAn8dCvkNbCqtUVcdik, прототипы иконки приложения: https://claude.ai/artifact/PBGGxgEGYZKHq1BBvPQRpx (читаются инструментом Artifact, `action: "read"`).

## Команды

```bash
./gradlew test assembleDebug   # тесты обоих вариантов и APK
./gradlew lintDebug            # lint
./gradlew testDebugUnitTest --tests 'com.ssortia.runtimer.WorkoutTest'   # один класс тестов
```

JDK 17 не прописан в профиле оболочки, и `java` нет в `PATH`. На этой машине JDK лежит в `~/.local/jdk-17`, на других путь свой: `JAVA_HOME=~/.local/jdk-17 ./gradlew test`.

Эмулятора и устройства в окружении нет. Звук, работу при выключенном экране и уведомления можно проверить только вручную на телефоне, не считайте их подтверждёнными по сборке и тестам.

## Соглашения

- Комментарии, строки интерфейса и документация на русском.
- Логика живёт в чистых функциях и классах без Android API и покрывается unit-тестами. Подписи и строки передаются в них параметрами. Код с Android API (сервис, Compose, Room, `AudioTrack`, `Vibrator`) держим тонким, он тестами не покрыт.
- KDoc только там, где поведение неочевидно.
- Настройки приложения (громкость сигналов, вибрация, приглушение музыки, задержка старта, тема) хранятся отдельными ключами в `SettingsStore`, а не в `WorkoutSettings` и не в интенте: сервис читает их в `startWorkout` и при выключенной вибрации не создаёт `Buzzer`, а при громкости 0 (`isSoundOn`) не создаёт `Beeper`: иначе он брал бы аудиофокус ради неслышного сигнала. Без `Beeper` из-за нулевой громкости предупреждения о звуке не показываются (`soundFailedWarning`, `soundMutedWarning`), пробного сигнала на 0 тоже нет. Громкость `snapVolume` приводит к шагу 10 с округлением половины вверх, в том числе старые значения с шагом 5. Числовые значения прижимаются к диапазону и при чтении, и при записи. Задержка старта выбирается из списка `START_DELAY_OPTIONS_SEC` с неравномерным шагом: ползунок ходит по индексам, а `snapStartDelay` приводит любое значение, в том числе старое 7 или 25, к ближайшему из списка.
- Планы лежат в `docs/plans/`, после ревью переносятся в `docs/plans/completed/`. Задачи лежат в `docs/tasks/`, выполненные переносятся в `docs/tasks/completed/`: выполненной считается задача, где осталась только ручная проверка на телефоне.
- При составлении плана через скил `planning:make` не спрашивайте, писать ли код по TDD или сначала код: по умолчанию сначала пишется код, затем тесты к нему. После создания плана не спрашивайте, что делать дальше (интерактивное ревью, авто ревью, implement, done): всегда сразу запускайте авто ревью. После авто ревью не предлагайте интерактивное ревью, оставьте на выбор только implement и done. При старте реализации не спрашивайте, работать интерактивно или автономно: план всегда реализуется автономно.
- При старте `planning:exec` не спрашивайте, останавливаться ли после каждого коммита для проверки кода: всегда выбирайте вариант «auto-commit» и выполняйте план полностью автоматически.

## Архитектура

Три слоя с однонаправленным потоком данных: UI (`MainActivity`, Compose-экраны), сервис (`WorkoutService`), логика, звук, вибрация и история (`Workout`, `WorkoutClock`, `tickAt`, `Beeper`, `Buzzer`, `runRecordOrNull`, `RunHistory`). `WorkoutClock` считает время тренировки за вычетом пауз, `Buzzer` дублирует сигналы вибрацией. Состояние лежит в `WorkoutService.state` в `companion object`, привязка к сервису не нужна. ViewModel и DI не используются намеренно: сервис один, а экран тренировки выбирается по состоянию. Навигация на Navigation Compose работает только внутри ветки `Idle` у `WorkoutScreen`: там `rememberNavController()` и `NavHost` с четырьмя строковыми маршрутами `settings` (стартовый), `app_settings`, `history` и `progress`, их константы и вкладки (`BottomTab`, `bottomTabOf`) лежат в `ui/BottomTab.kt`. Под `NavHost` стоит `NavigationBar` с вкладками «Тренировка» (`settings`), «История», «Прогресс» и «Настройки» и центральным слотом между «Историей» и «Прогрессом», где лежит доступный заместитель «Старта» (см. «Неочевидное»); выбранная вкладка берётся из маршрута `currentBackStackEntryAsState()`. «Старт» не вкладка: в `BottomTab` и `NavHost` его нет, видимая кнопка `StartFab` лежит поверх панели. Вкладки переключаются по схеме `if (!selected) navigate(route) { popUpTo(ROUTE_SETTINGS) { saveState = true }; launchSingleTop = true; restoreState = true }`: в стеке не больше двух записей, «Назад» с любой вкладки ведёт на форму, с формы закрывает приложение, а запись формы остаётся в стеке. Состояние вкладки (`rememberSaveable`, прокрутка) при переходе на другую вкладку сохраняется и возвращается через `restoreState`, а системная «Назад» снимает запись без сохранения, и следующее открытие вкладки начинается заново. После тренировки контроллер создаётся заново, и сохранённых состояний нет. Каждому маршруту `NavHost` соответствует вкладка `BottomTab`, `BottomTabTest` сверяет их набор. Иконка и подпись выбранной вкладки берут `primary`: индикатор M3 по умолчанию (`secondaryContainer` на `surfaceContainer`) в светлой теме почти не виден. Отступы `safeDrawing` сверху и по бокам поглощает общий `Box` ветки `Idle` (в нём `Column` с `NavHost` и панелью и поверх них `StartFab`) через `windowInsetsPadding(...only(Top + Horizontal))`, именно `windowInsetsPadding`, чтобы `NavigationBar` не добавил боковые второй раз, и именно `Box`, а не `Column`, чтобы при боковой системной панели «Старт» стоял по центру панели, а не экрана; снизу системную панель учитывает сам `NavigationBar` своими `windowInsets` по умолчанию. Клавиатуры вне тренировки нет (повторы меняются только кнопками), отдельный учёт `ime` не нужен. У экранов нет стрелки «Назад», у `AppTopBar` нет `onBack`, у формы в слоте `actions` плашка недели (`WeekChip`), открывающая шторку программы. Экраны отсчёта и тренировки маршрутами не становятся, ими управляет `WorkoutService.state`: при старте ветка `Idle` покидает композицию, стек сбрасывается сам, и после тренировки открывается форма. Переходы и возврат идут только через `NavController`. Колбэки внутри экранов `NavHost` обёрнуты в `dropUnlessResumed`, иначе двойное нажатие положит два экрана в стек или оставит пустой `NavHost`. У вкладок нижней панели и у «Старта» обёртки нет намеренно: панель стоит вне `NavHost`, её `LocalLifecycleOwner` — activity, а не запись стека, и обёртка не следила бы за переходом между экранами. Двойное нажатие безопасно и так: переход идемпотентен благодаря `popUpTo` и `launchSingleTop`, нажатие на текущую вкладку ничего не делает, а `popBackStack` вкладки не вызывают; повторный «Старт» отсекают `permissionPending` и сервис, отклоняющий второй запрос на старт. Своего `BackHandler` нет, системную «Назад» обрабатывает стек. Настройки формы (`WorkoutSettings`) хранит не запись стека, а ветка `Idle`: `rememberSaveable(stateSaver = WorkoutSettingsSaver) { mutableStateOf(loadSettings()) }` над `NavHost`, потому что «Старт» в панели виден на всех вкладках и запускает текущие, в том числе несохранённые, настройки (`onStart(settings)`), а его доступность `settings.validate() == null`. `SettingsContent` получает `settings` и `onSettingsChange`, раскрытая карточка и шторка программы остаются в `rememberSaveable` записи стека. При старте ветка `Idle` покидает композицию, поэтому после тренировки настройки читаются заново из `SettingsStore`. Текст ошибки показывается только на форме.

История пробежек: `RunRecord` одновременно чистая модель и `@Entity` Room, `RunDatabase.kt` содержит DAO, базу и `object RunHistory` (`runs`, `save`, `delete`). Экземпляр базы один на процесс и строится в `@Synchronized` функции `RunHistory`, а не в `by lazy`: для `Room.databaseBuilder` нужен контекст. Экземпляр берётся в вызывающем потоке до `launch`. Поля карточки собирает `runRowText` в `RunRowText.kt`, там же `groupRunsByMonth` группирует уже отсортированный список по месяцу старта в переданной зоне. Поток записей объявлен в `MainActivity` как `runs by lazy`, `HistoryContent` получает готовый список и про Room не знает. Схема экспортируется в `app/schemas/` через аргумент KSP и лежит в git, `fallbackToDestructiveMigration` не включён: смена `RunRecord` требует новой версии базы и миграции.

Прогресс по программе не хранится: маршрут `progress` собирает тот же поток `runs`, что и `history`, и считает `programProgress(records)` в `remember(records)`, поэтому удаление записи в истории сразу меняет прогресс, а схема базы для него не нужна. `programProgress` в `ProgramProgress.kt` отдаёт все 10 недель по порядку, считает только завершённые пробежки и не зависит от порядка списка (дата последней — максимум `startedAtMs`). Неделя пройдена при `RUNS_TO_PASS_WEEK` (4) пробежках, до этого кольцо закрашивает по части на пробежку. `WeekProgress` несёт свой `WorkoutPreset`, поэтому экран строит строки по `progress`, не сопоставляя его с `WORKOUT_PRESETS` по позиции. `ProgressContent` получает готовый `List<WeekProgress>?` и про Room не знает, при `null` показывает только `AppTopBar`. Текст строки недели (заголовок, параметры, число, дата или `null` для «—», описание кольца «Пробежек N из 4» или круга «Неделя пройдена»; у непройденной недели `runsSpoken = false`, и видимое число скрыто от TalkBack, чтобы не читалось дважды) собирает `progressRowText` в `ProgressRowText.kt`, дата последней пробежки форматируется там же явным шаблоном `d MMMM`, склонения «раз» и «из N недель» идут ресурсами `<plurals>` и передаются готовыми строками.

## Контракт сервиса

Нарушение этих правил даёт крэш или зависшую тренировку, а тесты его не поймают.

- `startForeground` идёт первым в `onStartCommand`, до всех проверок, даже если запрос будет отклонён. Заголовок берётся из последнего показанного текста `shownText`, а `app_name` только у нового экземпляра: на паузе текст не меняется, и цикл не вернул бы уведомление после команды.
- Команды паузы (`pauseIntent`, `resumeIntent`) идут через `startService()`: сервис уже на переднем плане. Они явные, а не переключатель, и безопасны при повторе. Без активной тренировки команда не содержит параметров и отклоняется существующим `stopSelf(startId)`, до создания `WorkoutClock` (отсчёт) и в финальном хвосте она ничего не меняет. Если команда пришла в уже уничтоженный экземпляр (например, «Стоп» и «Пауза» в одном кадре), система создаёт новый, и тот до `stopSelf(startId)` успевает показать уведомление с названием приложения (`app_name`). Поэтому кнопка паузы недоступна после финального сигнала (`pauseEnabled`).
- UI останавливает сервис только через `stopService()`, сам сервис завершается через `stopSelf()`. Вызов `startForegroundService()` ради остановки приведёт к крэшу.
- `onStartCommand` всегда возвращает `START_NOT_STICKY`. Потеря тренировки при гибели процесса принята для первой версии.
- `Countdown` и `Active` публикуются только после `startForeground`, иначе «Стоп» появится раньше времени.
- Окончательно ресурсы освобождает только `onDestroy`: отменяет цикл, отпускает `Beeper`, `Buzzer` и wake lock, снимает уведомление и последним ставит `Idle`. Финал лишь вызывает `stopSelf()`, поэтому форма появляется уже после освобождения ресурсов. Единственное исключение: на паузе wake lock снимается временно и при продолжении берётся заново на остаток тренировки плюс запас, поэтому `onDestroy` проверяет `isHeld`.
- `job` не обнуляется после финала: до `onDestroy` новый запрос на старт отклоняется.
- Запись истории собирается в `onDestroy` сразу после `scope.cancel()`, до остальных шагов: `saveRun()` берёт длительность из `clock.elapsedAt(...)`, а `workout` и `runStartedAtMs` из полей: оба заполнены раньше `clock`, поэтому проверяется только он. Сбой `RunHistory.save` ловится в `saveRun()` и пишется в лог, иначе `onDestroy` оборвался бы до освобождения ресурсов и `Idle`. Без `clock` (отклонённый запрос, команда паузы без тренировки, «Стоп» во время отсчёта) запись не собирается. Сохраняет её `RunHistory.save` в собственной области корутин на `Dispatchers.IO`, потому что `scope` сервиса уже отменён, без отдельного wake lock: после `onDestroy` процесс без сервиса может быть завершён, и wake lock от этого не спасает, а сон процессора только приостановит короткую вставку. `runStartedAtMs` заполняется перед созданием `WorkoutClock` и пересчитывается к моменту `startedAt` через `wallTimeAt`.

## Неочевидное

- `Beeper`: перед каждым проигрыванием нужны `stop()` и `reloadStaticData()`, иначе повторный сигнал будет беззвучным.
- `Beeper` берёт аудиофокус заранее через `duck()`: сервис вызывает его на каждом шаге цикла, когда до сигнала осталось не больше `DUCK_AHEAD_MS` (`shouldDuck`), и в конце отсчёта, иначе `stopDucking()`. `play()` переводит фокус на таймер возврата `soundWithTailMs`, а `duck()` этот таймер снимает, поэтому на коротких отрезках музыка остаётся приглушённой. `duck()` ничего не делает, если сигналы не готовы (`isReady`), и считает фокус взятым (`holding`) только при `AUDIOFOCUS_REQUEST_GRANTED`, поэтому после отказа следующий шаг цикла запросит его снова. Если `play()` не смог проиграть сигнал, он сразу возвращает фокус, взятый через `duck()`: таймера возврата в этом случае нет. Пауза возвращает фокус сразу в `handlePauseAction`, до снятия wake lock, а продолжение сразу приглушает музыку, если до сигнала не больше `DUCK_AHEAD_MS` (`shouldDuckAfterResume`): цикл без wake lock может не проснуться, а на следующем шаге приглушать уже поздно. Окончательно фокус отпускает `release()`, у `Beeper` сервиса это `onDestroy`. Каждый отрезок кончается сигналом, поэтому сервис считает время до сигнала по `position.remainingMs`; если это изменится, `shouldDuck` надо кормить другим временем. Настройка «Приглушать музыку» передаётся обеим функциям обязательным `duckMusic` и в конструктор `Beeper`: при `false` фокус не берут ни `duck()`, ни `play()`, и сигнал звучит поверх музыки в полную громкость. Её хранит прежний ключ `duck_ahead`, чтобы сохранённое значение не сбросилось.
- Пробный сигнал ползунка играет собственный `Beeper` в `MainActivity`, он готовит только `INTERVAL`. Его отпускают перед новым пробным сигналом, при уходе состояния из `Idle` и в `onStop`, иначе дорожка и аудиофокус переживут экран или будут жить всю тренировку рядом с `Beeper` сервиса. Все методы `Beeper` вызываются только из главного потока: таймер возврата фокуса работает на `Handler(Looper.getMainLooper())`.
- Канал `Beeper` (`USAGE_ASSISTANCE_NAVIGATION_GUIDANCE`) считается следующим громкости медиа, поэтому `isMediaMuted()` и `volumeControlStream` в `MainActivity` смотрят на `STREAM_MUSIC`. При смене атрибутов `Beeper` обе строки надо пересмотреть, тесты это не поймают.
- Атрибуты `Beeper` объявлены в `companion object`, до `tracks`: поле экземпляра ниже `tracks` было бы ещё `null`, `AudioTrack.Builder` бросил бы исключение, и `catch` молча оставил бы тренировку без сигналов при зелёных тестах.
- Итоговая громкость сигнала равна настройке приложения, умноженной на системную громкость канала: `setVolume()` только ослабляет звук.
- Звуки отсчёта, старта, смены отрезка и финала (`signal_countdown`, `signal_start`, `signal_interval`, `signal_finish`) лежат в `res/raw` и должны быть WAV PCM 16 бит моно 44,1 кГц, иначе `decodeWav` их отклонит и сигнала не будет. Звук отсчёта должен быть короче 1 с: «2» и «1» идут с интервалом в секунду, `SignalFilesTest` это проверяет. Их длительности продублированы константами `COUNTDOWN_SOUND_MS`, `START_SOUND_MS`, `INTERVAL_SOUND_MS` и `FINISH_SOUND_MS`, потому что по ним держится фокус и ждёт финал, а файлы читаются только с Android API. `SignalFilesTest` сверяет константы с файлами, при замене звука обновите обе. Файлы готовились так: `ffmpeg -i in.mp3 -af "atrim=start=0.06:end=…,asetpts=N/SR/TB,pan=mono|c0=0.5*c0+0.5*c1,aresample=44100,afade=t=in:d=0.005,afade=t=out:st=…:d=0.03" -c:a pcm_s16le -map_metadata -1 tmp.wav && sox tmp.wav out.wav gain -n -2`.
- `FINISH_TAIL_MS` нельзя убирать: `release()` сразу после конца буфера обрезает финальный сигнал.
- `START` подаётся отдельным вызовом в `runLoop`, мимо `tick.signal`, и правило «только при задержке > 0» тестами не покрыто. `COUNTDOWN` («2» и «1») выдаёт `countdownTickAt` при пересечении границ `COUNTDOWN_SIGNALS_AT_MS` с прошлого шага (`previousRemainingMs`), и `runCountdown` проигрывает его отдельно от цикла тренировки. Всё новое, что реагирует на сигналы, надо добавлять во все три места (`runCountdown`, `START` в `runLoop`, `tick.signal`), как сделано для `Buzzer`. В отсчёте приглушение считается по `msToNextCountdownSignal`, а не по времени до старта: первый сигнал звучит за 2 с до него.
- Ожидание после финала равно большей из длительностей звука и вибрации плюс `FINISH_TAIL_MS`: что из них длиннее, зависит от звука финала и паттернов, а `onDestroy` оборвала бы более длинное.
- Во время отсчёта `startedAt` лежит в будущем, поэтому `WorkoutClock` создаётся в `runLoop` только после отсчёта: иначе прошедшее время было бы отрицательным. Команда паузы может прийти раньше, поэтому без часов `handlePauseAction` её игнорирует (`clock ?: return`).
- На паузе wake lock снимается сразу, хотя `Beeper` может ещё держать фокус до `soundWithTailMs`, а его таймер на `Handler` во сне процессора стоит. Это допустимо: пока играет музыка, её вывод сам не даёт процессору уснуть, а без музыки удержанный фокус никому не мешает.
- `Buzzer` вызывает перегрузку `vibrate(VibrationEffect, AudioAttributes)` с `@Suppress("DEPRECATION")` намеренно: замена с `VibrationAttributes` есть только с API 33, а `USAGE_ALARM` нужен, чтобы система не глушила вибрацию при выключенном экране и в беззвучном режиме. Атрибуты `Beeper` (`USAGE_ASSISTANCE_NAVIGATION_GUIDANCE`) для вибрации не подходят по той же причине.
- Правило допустимых параметров записано дважды: в `WorkoutSettings.validate()` для формы и в `workoutOrNull()` для сервиса. Меняйте их вместе, иначе форма пропустит настройки, а сервис молча отклонит запрос. Нулевой шаг допустим только при одном повторе (неделя 10 программы).
- Неделя записи истории (`presetWeekOf(record)`) определяется сравнением `Workout` записи с `preset.settings.toWorkout()`, а шаг берётся из `RunRecord.effectiveWalkSec`, который при одном повторе даёт 0: такой шаг не выполняется (по тому же правилу его не показывает `runRowText`), а форма разрешает его задать, поэтому «Бег 30:00, Шаг 2:00, ×1» засчитывается неделе 10. Сравнение через `toWorkout()` нужно, чтобы 1 мин 30 сек недель 5–6 совпадали с 90 секундами записи. Цвета экрана прогресса: закрашенные части и деления берут `segmentColors(isRun = true, …).marker`, а не `primary`, незакрашенные `progressTrackColor`, галочка `progressCheckColor` из `ui/Theme.kt`. `ThemeTest` в обеих темах требует контраст `marker` на дорожке не меньше 3:1, дорожки на `surfaceContainer` не меньше 1,3:1 (дорожка фоновая, смысл несут закрашенные части и подпись) и галочки на `marker` не меньше 3:1.
- Неделя в `RunRecord` не хранится: `presetWeekOf(record)` вычисляет её по текущему `WORKOUT_PRESETS`, поэтому смена параметров недели задним числом меняет прогресс, а старые записи с прежними параметрами перестают засчитываться. Тройки (бег, шаг с учётом `effectiveWalkSec`, повторы) у недель должны оставаться разными, иначе запись достанется первой из совпавших.
- Значения по умолчанию в `WorkoutSettings` совпадают с неделей 1 из `WORKOUT_PRESETS`, поэтому при первом запуске она отмечена в шторке программы и написана на плашке справа от заголовка формы (при несовпадении с неделями там «Своя тренировка»). При смене значений по умолчанию или программы `WorkoutPresetTest` это поймает.
- `MainActivity.startWorkout()` читает настройки из `SettingsStore`, а не из замыкания: ответ на запрос разрешения может прийти в новый экземпляр activity.
- `permissionPending` блокирует второй запрос разрешения: система отклоняет его сразу, и тренировка запустилась бы за диалогом.
- Тема (`ThemeMode`) хранится ключом `theme_mode` по имени значения, неизвестное имя читается как `SYSTEM`. Выбор держит `MainActivity` в состоянии Compose, а не экран настроек: он применяется ко всему UI сразу. Признак тёмной темы считается только там (`isDarkTheme(mode, isSystemInDarkTheme())`) и раздаётся через `LocalDarkTheme` из `RunTimerTheme`; прямой вызов `isSystemInDarkTheme()` в экране разведёт цвета отрезков с выбранной темой. Системная панель навигации (`navigationBarStyle` в `enableEdgeToEdge`) и фон окна тоже задаются по этому признаку, а не по системной теме. На форме (`Idle`) стиль панели `light`/`dark` с прозрачным цветом: под ней лежит фон `NavigationBar`, а подложка кнопок, в том числе принудительный контраст API 29+ у стиля `auto`, сделала бы полосу двухцветной. На отсчёте и тренировке остаётся `auto` с подложкой: фон цветной, а значки панели следуют за темой. На API 31+ выбор дополнительно передаётся `UiModeManager.setApplicationNightMode()` (`SYSTEM` это `MODE_NIGHT_AUTO`): система применяет его к окну и заставке до старта процесса, а пересоздания activity нет: она объявляет `configChanges="uiMode"`, иначе смена темы давала чёрный кадр. Поэтому всё, что зависит от темы, должно браться из Compose (`LocalConfiguration`, `LocalDarkTheme`) или переприменяться по признаку в `setContent`, как фон окна и системные панели: тема окна из `values-night` после запуска уже не обновится. В `onCreate` он не повторяется, поэтому после восстановления настроек из резервной копии заставка может быть в системной теме до следующей смены. Константы `MainActivity.kt` уровня файла не должны вызывать Android API (`Color.argb`): файл загружается в unit-тестах, и инициализатор уронил бы их.
- Анимации `NavHost` отключены (`EnterTransition.None`, `ExitTransition.None`) намеренно: во время перехода экран не `RESUMED`, и `dropUnlessResumed` глотал бы нажатия. Уходящий экран всё равно остаётся в композиции кадр-другой, поэтому маршруты объявляются через `screen()` с непрозрачным фоном, а не через `composable()` напрямую, иначе экраны на миг накладываются.
- У области корутин `RunHistory` нет `CoroutineExceptionHandler` намеренно: ловится только `SQLiteException`, любое другое исключение при записи или удалении роняет процесс, и запись теряется, зато ошибка разработки не прячется.
- `.catch` в `RunHistory.runs` ловит только `SQLiteException`, пишет её в лог и завершает поток без нового значения: `HistoryContent` показывает последний полученный список или ничего (`null`), а не «Пробежек пока нет», а `ProgressContent` из того же потока прогресс по последнему списку или только `AppTopBar`, а не «0 из 10», до следующего возврата экрана в `STARTED`, когда `collectAsStateWithLifecycle` подпишется заново. `IllegalStateException` от Room (смена схемы без миграции) не ловится намеренно.
- Признак «завершена» выводится из длительности (`elapsedMs >= workout.totalMs`), а не отмечается в момент `tick.finished`: после финала часы идут дальше, поэтому «Стоп» во время финального сигнала тоже даёт «завершена», а длительность прижимается к `totalMs`. Правило 30 секунд (`MIN_STOPPED_RUN_MS`) считается по времени без пауз.
- Полная дата старта `RunRowText.date` (диалог удаления и описание корзины, в карточке её нет) форматируется явным шаблоном `d MMMM yyyy, HH:mm`, а не `ofLocalizedDateTime`: локализованный формат в JDK берётся из CLDR, а на телефоне из ICU, и тест сверял бы не то, что видит пользователь. Остальные форматы истории тоже явные: день `d`, день недели `EEE`, время `HH:mm`, месяц `LLLL yyyy` (самостоятельная форма «ноябрь»). `EEE` и `LLLL` на телефоне берутся из ICU, их совпадение с JDK проверяется только вручную. Длительность там округляется вниз до секунды через `formatElapsed`, хотя `formatTotal` округляет вверх. Все форматы собраны в `RunFormatters` и создаются `runFormatters(zone, locale)` один раз на экран.
- В диалоге удаления `HistoryContent` хранит в `rememberSaveable` только `pendingDeleteId`: `RunRecord` не `Parcelable`, и сохранение состояния уронило бы приложение. Если записи с этим `id` в полученном списке нет, `id` сбрасывается, иначе диалог всплыл бы позже. Удаление идёт через область корутин `RunHistory`, а не `lifecycleScope`, который оборвал бы его при закрытии activity.
- Цвета задаются только в `ui/Theme.kt` (`appColorScheme`, `SegmentColors`) и в `colors.xml` (фон окна, `RunTimerTheme` подставляет его в `background` и `surface`), экраны литералов цвета не заводят. Рамка плашки недели берёт `weekChipBorderColor(dark)`, `ThemeTest` требует её контраст на `background` не меньше 1,3:1, а текста плашки `onSecondaryContainer` на `secondaryContainer` не меньше 4,5:1. `surfaceTint` прозрачный, иначе шторка и диалог с `tonalElevation` подмешивают акцент к фону. Точки отрезков на форме берут `SegmentColors.marker`, а не `background`: тёмный фон шага на тёмной карточке почти не виден, `ThemeTest` требует контраст `marker` на `surfaceContainer` не меньше 3:1. Пользователь выбрал белый текст на изумрудном `#047857` в обеих темах, но в тёмной теме у него на карточках контраст около 3:1, поэтому `primary` тёмной схемы светлый `#34D399` (текст и значки акцента: кнопки диалога, время раскрытой карточки, галочка истории, `Switch`, `Slider`), а «Старт» в панели (`StartFab`) явно берёт цвета бега из `segmentColors`; недоступный берёт `onSurface` 12 % и 38 % как у M3, но заливка смешана с фоном (`compositeOver`), иначе сквозь полупрозрачную кнопку проступала бы граница панели. `ThemeTest` требует `primary` на `surfaceContainerLow`, `surfaceContainer` и `surfaceContainerHigh` не меньше 4,5:1 в обеих темах. Новая залитая кнопка в стиле «Старт» тоже должна брать цвета бега, а не `primary`.
- Бег (`#047857`) и шаг различаются оттенком, а не яркостью: контраст их фонов меньше 3:1, поэтому `ThemeTest` проверяет разницу тонов не меньше 40° (у выбранных цветов 45°). Новые цвета отрезков должны пройти этот тест и контраст текста 4,5:1.
- Барабан секунд строится как `wheelOptions(MAX_SECONDS, SECONDS_WHEEL_STEP, …)`: значение не на шаге 5, в том числе допустимое 56–59, вставляется в список на своё место, а не прижимается, иначе открытие барабана молча меняло бы настройку. Состояние формы — сам `WorkoutSettings` в `rememberSaveable` с `WorkoutSettingsSaver` в ветке `Idle`, значения хранятся как есть, без прижатия. Барабаны и степпер пишут в его поля, проверка и сохранение формы от них не зависят. Остановка сравнивается с сохранённым значением (`wheelPick`), а не с показанной строкой: иначе неверное сохранённое (120 минут показаны как 99) нельзя было бы подтвердить. Сворачивание карточки посреди прокрутки фиксирует строку в середине, а внешняя смена значения (неделя из шторки) прерывает инерцию через `scrollToItem`.
- `SectionTitle` (заголовки групп настроек и месяцев истории) рисует текст прописными, а для TalkBack через `clearAndSetSemantics` отдаёт исходную строку с `heading()`: прописное слово часть синтезаторов читает по буквам. Группа радиокнопок темы без видимой подписи, её имя «Тема» задано описанием `selectableGroup`.

Отступ кнопки снизу — нижние `NavigationBarDefaults.windowInsets` (те же, что у самой панели) плюс `BottomBarHeight` минус (`StartFabSize` − `StartFabOverlap`). `BottomBarHeight` (80 dp) повторяет внутреннее `NavigationBarHeight` M3, которое наружу не открыто: при его смене в новой версии M3 выступ разойдётся с панелью, тесты это не поймают. Кнопка 72 dp: заливка 64 dp и кольцо цвета фона 4 dp, `BorderStroke` рисуется внутри границ.
- Для TalkBack видимая кнопка скрыта (`clearAndSetSemantics {}`, у значка `contentDescription = null`), а «Старт» читает заместитель в центральном слоте `NavigationBar`: `Box(weight(1f).height(BottomBarHeight))` с `clickable` без ряби (`indication = null`), ролью кнопки, тем же `enabled` (он сам ставит `disabled()` при неверных настройках) и описанием `button_start`. - «Старт» выступает над панелью на `StartFabOverlap` (треть его высоты, 24 dp: две трети кнопки лежат на панели) на каждой вкладке, поэтому все прокручиваемые колонки (формы, истории, прогресса, настроек) берут нижний отступ `ScrollContentBottomPadding` (16 dp + выступ), у `LazyColumn` через `contentPadding`. Новый прокручиваемый экран вкладки должен брать его же, иначе кнопка закроет последний элемент.

- `weight` внутри `verticalScroll` не работает, поэтому свободное место итогу раздаёт `SubcomposeLayout` (`FormLayout` в `SettingsContent.kt`) внутри `BoxWithConstraints`: область `viewport = constraints.maxHeight − FormTopPadding − ScrollContentBottomPadding` в пикселях, каждый отступ округлён `roundToPx()` так же, как его округляет колонка (без вычета отступов колонка прокручивалась бы всегда, а округление в dp могло дать лишний пиксель прокрутки). Сначала меряется нижняя часть (карточки, предупреждение, ошибка), затем итог с `displayLarge`. Решение принимает только чистая `summaryPlacement` (`ui/SummaryPlacement.kt`): крупный берётся, если влез по высоте и его время не шире строки (ширину меряет `rememberTextMeasurer` тем же стилем `summaryTimeStyle`), иначе она вызывает переданную лямбду, и раскладка только тогда составляет и меряет итог с `displayMedium`. Малый берётся, даже если не влез и он, слот итога `max(свободное, высота итога)`, высота раскладки слот плюс нижняя часть, то есть не меньше области, а больше неё колонка прокручивается и итог уходит вверх. Прокрутка обратная (`verticalScroll(..., reverseScrolling = true)`): смещение отсчитывается от нижнего края, поэтому при первом открытии видны карточки у панели, а при любой смене высоты (раскрытие карточки, предупреждение, ошибка, шрифт) сохраняется смещение от низа, и раскладка растёт вверх; с обычной прокруткой смещение 0 показывало бы итог, а карточки уходили бы за нижний край. Сохранённое `rememberScrollState` значение тоже отсчитано от низа. Итог стоит по центру слота. Размещается только выбранный вариант: неразмещённый не попадает в дерево доступности, иначе TalkBack нашёл бы два итога. Подпись «Вся тренировка» мелкая (`bodyMedium`).
